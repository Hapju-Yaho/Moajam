# 악보 재생바 끊김 원인 분석

> 표시 정책 변경: 재생바와 개별 음표 강조를 제거하고 현재 마디 배경만 강조한다. 아래 전후 측정은 당시 재생바·음표 강조가 있던 조건의 기록이다. 현재 코드는 커서 좌표 보간, 음표별 재생 구간 조회, 음표 강조용 SVG도 생성하지 않는다. 선택 사항인 메트로놈 박자 표시와 마디 전환 스크롤은 유지한다.

## 개선 전 구조

- `ScoreEditorScreen.web.tsx`의 오디오 스케줄러는 40ms마다 실행된다. React의 `playbackBeat`는 박이 바뀔 때 갱신된다.
- 재생바 자체는 `scorePlaybackDisplay.web.ts`의 `requestAnimationFrame`에서 오디오 시계를 읽어 이동한다. 재생바가 박마다만 이동하도록 구현된 것은 아니다.
- 그러나 박 상태가 바뀌면 악보 편집기와 오선 렌더링이 다시 실행된다. `GuitarStaff.web.tsx`에서는 시스템별 마디·간격·음표 배치 계산을 렌더링 중 수행한다. 화면 밖 SVG 가상화가 있어도 그 앞의 레이아웃 계산까지 모두 생략되는 구조는 아니다.
- `useScorePlaybackDisplay`의 `useLayoutEffect`에는 의존성 배열이 없다. React 렌더마다 기존 프레임 루프를 정리하고, DOM 조회·위치 JSON 파싱·재생 대상 캐시 생성을 다시 수행한다. `useLayoutEffect` 작업은 화면 그리기 전에 실행된다.
- 참조 음원이나 유튜브를 함께 재생하면 시간 표시용 `setAudioPosition`도 최대 250ms마다 부모 화면을 갱신한다. 이 조건에서는 추가 렌더가 발생할 수 있다.
- 줄 전환 시 자동 스크롤은 스크롤 조상들의 스타일과 위치를 읽고 부드러운 이동을 실행한다. 이 부분은 줄 경계에서 추가 부하가 될 가능성이 있으나, 이번 측정으로 기여도를 따로 확정하지 않았다.

## 브라우저 측정

Vite 개발 환경의 headless Chrome, 1440×1050, 음표 2,000개인 메모리 전용 검증 악보를 사용했다. 실제 사용자 프로젝트나 서버 DB는 수정하지 않았다. 실제 음원을 재생하는 대신 연속 시간 참조를 120 BPM처럼 진행시키고, React 박 갱신 유무를 비교했다. 각 구간은 약 4초이며, 초기 준비 이후를 측정했다.

| 조건                                     | React 커밋 | React 렌더 평균 / 최대 | 프레임 간격 95백분위 / 최대 |
| ---------------------------------------- | ---------: | ---------------------: | --------------------------: |
| 연속 재생바 갱신만                       |        0회 |              해당 없음 |               16.8 / 16.8ms |
| 같은 애니메이션에 박마다 React 갱신 추가 |        7회 |          55.9 / 67.4ms |               16.8 / 66.6ms |

60fps의 프레임 예산은 약 16.7ms다. 대부분의 프레임은 정상이어도 박 상태 갱신 때 약 50~67ms의 작업이 끼면 일부 프레임이 빠지며 재생바가 순간적으로 끊길 수 있다. 관찰한 간헐적 끊김을 재현하는 결과다.

이 수치는 개발 빌드·테스트 기기·대용량 검증 악보에서의 결과다. 사용자가 보고한 곡 자체의 측정값이나 운영 빌드 성능을 뜻하지 않으며, 실제 오디오 출력의 끊김 여부도 이 실험으로 판단하지 않는다.

## 개선 우선순위

1. 음표 배치와 SVG 렌더링을 재생 위치 상태에서 분리한다. 악보 데이터·배율·레이아웃이 바뀔 때 배치를 계산하고, 재생 중에는 커서·강조·박자 원만 갱신한다.
2. 재생 표시 효과의 재시작 조건을 실제 DOM/레이아웃 변경과 재생 시작·종료로 제한한다. 도구 모음 시간 갱신 때문에 DOM 캐시와 프레임 루프를 재생성하지 않도록 한다.
3. 마디·박 표시, 믹서 재생 표시와 참조 음원 시간 표시를 작은 컴포넌트로 분리해 전체 편집기 렌더를 줄인다.
4. 이후 실제 문제 곡과 운영 빌드에서 줄 전환·반복 재생·참조 음원 동시 재생을 따로 측정한다.

## 적용한 개선 (2026-10-28)

- 오디오 스케줄러의 박별 `setPlaybackBeat`를 제거했다. 편집기에는 재생 시작·종료를 전달하고, 연속 위치는 오디오 시계 참조로 읽는다. 재생 위치 갱신 때문에 음표 배치 계산과 전체 SVG 렌더를 다시 하지 않는다.
- 마디·박 문구, 이전/다음 마디 버튼, 믹서 마디 강조, 참조 음원 시간 표시를 작은 구독 컴포넌트로 분리했다. `scorePlaybackSubscription.web.ts`가 시계별 프레임 루프를 공유하며, 각 컴포넌트는 자신이 표시하는 값이 바뀔 때만 렌더한다. 참조 시간은 재생 중 부모 상태를 갱신하지 않고 정지할 때만 최종 값을 전달한다.
- 재생 표시 효과의 시작·종료 조건을 고정했다. DOM 캐시는 악보 줄이 생성·제거되거나 위치 메타데이터가 변경될 때만 다시 읽는다. 시간 문구, 커서 이동, 강조 속성 변경은 캐시를 무효화하지 않는다.
- 가상화된 악보 줄도 같은 시계를 구독해 필요한 줄만 표시한다. 자동 스크롤은 실제 재생 줄이 바뀔 때 수행하고, 현재·다음 마디 원과 음표 강조는 DOM 속성으로 갱신한다.
- 악보 오디오 스케줄링은 기존 구조를 유지했다. Web Worker나 서버/DB 변경은 없다.

## 개선 후 측정

앞의 동일한 2,000개 음표 개발용 검증 악보에서, 새 구조와 같이 부모의 박별 갱신 없이 연속 시계를 진행시켰다. 마디·박 표시용 작은 컴포넌트만 갱신됐다.

| 조건                             | React 커밋 | React 렌더 평균 / 최대 | 프레임 간격 95백분위 / 최대 |
| -------------------------------- | ---------: | ---------------------: | --------------------------: |
| 개선 전: 박마다 전체 편집기 갱신 |        7회 |          55.9 / 67.4ms |               16.8 / 66.6ms |
| 개선 후: 표시 컴포넌트만 갱신    |        8회 |          0.29 / 0.90ms |               16.8 / 16.8ms |

추가 회귀 검증은 `scripts/score-playback-clock.browser.tsx`에서 수행했다. 2,000개 음표·250마디, 믹서와 참조 시간 표시를 포함한다. 개발 빌드에서 일반 진행은 평균 0.22ms / 최대 2.60ms, 반복 진행은 평균 0.17ms / 최대 2.30ms의 작은 React 렌더만 발생했다. 두 경우 모두 측정 중 부모 편집기 렌더 횟수는 증가하지 않았다.

동일 회귀 검증의 운영 빌드에서도 일반 진행·반복 복귀·76마디로 화면 밖 이동·처음 마디로 복귀를 확인했다. 프레임 간격 95백분위와 최대는 이 테스트에서 약 16.8ms였다. 운영 React의 기본 Profiler 콜백은 비활성화되므로 운영 빌드의 React 커밋/시간은 측정값으로 해석하지 않는다. 대신 부모 렌더 계수, SVG 노드 유지, 박 이동 중 DOM 캐시 재조회 없음, 믹서·마디 문구·음표 강조 및 정지 후 정리를 검사한다.

이는 메모리 검증 악보와 모의 연속 시계의 결과다. 참조 시간 표시를 함께 갱신했지만 실제 음원 출력·YouTube 통신은 포함하지 않았다. 사용자가 문제를 겪은 실제 곡, 모바일 기기, 실제 참조 음원 동시 출력의 성능은 별도 측정이 필요하다.

## 재현 방법

저장 데이터에 접근하지 않는 전용 검증 화면을 사용한다. 저장소 루트에서 아래 명령으로 개발 서버를 켜고, 다른 터미널에서 테스트한다. Chrome 기본 설치 경로가 다르면 `CHROME_PATH`를 지정한다.

```powershell
node node_modules/vite/bin/vite.js --config scripts/score-playback.vite.config.mts --host 127.0.0.1 --port 5188 --strictPort
node scripts/score-playback-clock.test.mjs
```

운영 빌드 검증은 전용 출력 폴더 `.tmp/score-performance-dist`를 사용한다. preview를 실행한 터미널은 유지하고, 다른 터미널에서 테스트한다.

```powershell
node node_modules/vite/bin/vite.js build --config scripts/score-playback.vite.config.mts
node node_modules/vite/bin/vite.js preview --config scripts/score-playback.vite.config.mts --host 127.0.0.1 --port 5189 --strictPort
```

```powershell
$env:SCORE_TEST_URL='http://127.0.0.1:5189/scripts/score-playback-clock.browser.html?backing'
node scripts/score-playback-clock.test.mjs
Remove-Item Env:SCORE_TEST_URL
```

전체 웹 빌드, 앱 TypeScript 검사, 변경 파일 ESLint, 악보 관련 단위 테스트 77개도 통과했다.

## 타브 전용 보기

타브 전용 모드는 오선 영역을 만든 뒤 `viewBox`로 잘라내지 않는다. 오선의 음높이 좌표·임시표·화음 충돌·줄기·빔 배치를 생략하고, 오선 SVG도 생성하지 않는다. 타브 줄을 기준으로 세로 배치를 계산하며 마디의 가로 배치와 박자, 타브 리듬·주법·코드·재생 표시는 유지한다. 꾸밈음과 연결선도 타브 표시만 생성한다.

회귀 검증: `node --test scripts/score-tab-only.test.mjs`. 오선 요소 부재, 오선 음높이에 영향받지 않는 타브 레이아웃, 편집·재생 대상 및 주법 보존을 확인한다. 실제 곡별 프레임 시간 개선 폭은 별도 측정이 필요하다.
